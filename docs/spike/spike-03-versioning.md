# Spike 03：草稿→已发布与历史不覆盖探针

> 状态：**待执行**（本次仅起草计划，未执行） · 日期：2026-11-11 · 关联 [`adr/001-technology-stack.md`](../adr/001-technology-stack.md) 方案 B
> 验证目标：M03 的 AC-03-06、M05 的 AC-05-06、M08 的 AC-08-07
> 执行需团队授权，在独立验证环境进行；**不写入 `src/`**。本周不写业务代码，本文件是计划而非已执行结果。

## 1. 目的

在 MySQL 8 上验证训练计划/饮食建议的"草稿 → 已发布"状态流转，以及"新周期发布不覆盖历史执行记录所对应的那一版内容"——这是 `spec/mvp1-scope.md` 第 3.1 节"历史不可覆盖"的关键证据。

## 2. 前置条件

- MySQL 8 最小探针环境（独立目录，不写入项目 `src/`）。
- 虚构数据：P-001 已发布训练计划（ACT-001 / 3 组 / 10 次），R-001 为 T-001 针对 P-001 的执行记录，N-002 已发布饮食建议。

## 3. 输入（用例集）

| 用例 | 操作 | 期望 |
| --- | --- | --- |
| S03-1 | 草稿 D-001 经教练确认发布 → P-001 | 状态 draft→published，T-001 可见 |
| S03-2 | 发布下一周期 P-002（4 组 / 8 次） | R-001 仍对应 P-001 的 3 组 / 10 次 |
| S03-3 | 发布下一周期饮食建议 N-003 | 上一周期餐食文字记录仍对应 N-002 |
| S03-4 | 查询 R-001 的历史计划 | 返回 P-001 当时内容，不含 P-002 |

## 4. 执行步骤

1. 设计计划/建议表与版本表：发布生成不可变版本记录，执行记录关联版本 ID。
2. 插入 P-001 已发布版本与 R-001（关联 P-001 版本 ID）。
3. 发布 P-002，查询 R-001 对应计划，比对内容。
4. 对饮食建议重复 S03-3。
5. 记录表结构、版本 ID 关联与查询结果。

## 5. 要记录的字段

| 项 | 值 |
| --- | --- |
| 用例编号 | S03-N |
| 版本表结构 | 字段与关联方式 |
| R-001 关联的版本 ID | |
| 查询返回内容 | 是否为 P-001 的 3 组 / 10 次 |
| 是否被 P-002 覆盖 | 是 / 否（须为"否"才算通过） |
| 完成率依据版本 | M08 计算时所取的计划版本是否正确 |

## 6. 判定标准

- **通过**：S03-2/S03-4 中 R-001 始终对应 P-001 当时的动作与组次，不被 P-002 覆盖；饮食建议同理。
- **失败**：新周期发布后，历史执行记录对应的内容被改写或丢失。

## 7. 结论边界

- 能证明：方案 B + MySQL 的版本化方案能满足"历史不可覆盖"与完成率取当时版本的要求。
- 不能证明：计划编排 UI、公共动作停用对历史的影响（AC-09-08 另验）、AI 草稿生成本身（见 spike-01）。
- 不代替 M03、M05、M08 的完整业务验收。

## 8. 风险与替代

- 版本表设计过重：若全量冗余成本高，改为"已发布快照 + 当前草稿"两表，或在执行记录中冗余当时计划关键字段。
- 误用软删除导致历史丢失：明确已发布版本不可删除、不可原地改写，仅可新增版本。
