# Spike 01：AI 草稿生成契约探针

> 状态：**待执行**（本次仅起草计划，未执行） · 日期：2026-11-11 · 关联 [`adr/001-technology-stack.md`](../adr/001-technology-stack.md) 方案 B
> 验证目标：M04 的 AC-04-01 / 03 / 04
> 执行需团队授权，在独立验证环境进行；**不写入 `src/`、不提交密钥、不进仓库日志**。本周不写业务代码，本文件是计划而非已执行结果。

## 1. 目的

用 DeepSeek（OpenAI 兼容口）经 Spring Boot 后端生成一次训练计划草稿，验证 M04 的输入字段、输出结构、校验规则、超时与重试、费用能否落地，并为方案 B 的 AI 集成提供证据。

## 2. 前置条件

- DeepSeek API Key：放本地 `.env`，由后端读取，不进仓库、不下发浏览器。
- Spring Boot 3.x 最小可运行探针环境（独立目录，不写入项目 `src/`）。
- 虚构档案 T-001：增肌 / 初级 / 每周 3 次 / 可用器械「哑铃」（见 `spec/mvp1-scope.md` 第 8 节）。
- 公共动作 ACT-001「哑铃卧推」可用。

## 3. 输入

- 系统提示：要求模型按给定 JSON Schema 输出一周训练计划，字段含训练日期、动作、组数、次数、建议重量。
- 用户消息：T-001 档案四字段 + 教练本次输入（如「本周重点胸部、强度中等」）。

## 4. 执行步骤

1. 后端用 HTTP 客户端（RestClient 或 WebClient）调用 DeepSeek `chat/completions`，启用 JSON 输出。
2. 用 T-001 档案 + 教练输入生成一周训练计划草稿。
3. 记录请求体、响应体、耗时、token 数与费用。
4. 校验输出字段完整性与训练条件符合性（动作是否限在哑铃）。
5. 故意触发失败用例并分别记录：空档案、模拟超时、无效 Key、返回缺字段。

## 6. 判定标准

- **通过**：正常用例输出五字段齐全且动作符合哑铃条件；失败用例明确提示、不产生可用草稿、保留人工编写路径、不把模拟返回显示为真实成功。
- **失败**：输出缺字段或不符合条件且未提示；或失败时仍显示"生成成功"。

## 7. 结论边界

- 能证明：DeepSeek + Spring Boot 能满足 M04 的契约与失败处理要求，以及单次调用费用量级。
- 不能证明：前端展示、服务端权限、历史版本不覆盖、饮食建议生成（M05 另参考本探针结构）。
- 不代替 M04 的完整业务验收。

## 8. 风险与替代

- 输出不稳定或费用超预算：切换 OpenAI 兼容口的智谱 GLM 或通义千问，后端调用代码基本不变。
- JSON 输出不可靠：改为函数调用 / 结构化输出模式，或在后端做解析与补全。
- 替代服务商的费用与可用性须在本探针中并列记录。
